# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Overview

BlindsUP is a single-file poker blinds timer — all HTML, CSS, and JavaScript live in `index.html` (plus a small `sw.js` service worker for offline caching). There is no build step, no package manager, and no test framework, and no vendored third-party libraries — the entire app is hand-written JS in one inline `<script>` block, including a small adapted synth (`zzfx`) for sound effects.

## Workflow

Always commit and push every change immediately after making it — no need to ask for confirmation first.

## Running the app

Open `index.html` directly in a browser, or serve it with any static file server:

```
npx serve .
# or
python -m http.server
```

## Architecture

Everything is in `index.html`. The structure is:

- **CSS** (`:root` variables → screen layouts → component styles → animations)
- **HTML** — two top-level screens: `#menu-screen` and `#app`
- **JavaScript** — no modules, no classes, plain procedural script at bottom of `<body>`

### State

All mutable state is global:

| Variable | Purpose |
|---|---|
| `level` | Current blind level (1–25, see Blind schedule) |
| `remSec` / `pausedRemSec` | Remaining seconds; `pausedRemSec` is the snapshot saved at pause |
| `paused` / `running` | Timer state |
| `launchWall` | `Date.now()` at last resume — elapsed time is computed as `(Date.now() - launchWall) / 1000` |
| `advancing` / `snapTO` | True during the brief window between a level auto-advancing and its RTC-aligned start landing (see RTC alignment below) |
| `pauseSecRTC` | RTC second-of-minute recorded at pause, used to correct drift on resume |
| `audioCtx`, `alarmNodes`, `alarmTimeouts` | Web Audio API context and active oscillator nodes / pending sound timeouts |

### Blind schedule

`BLINDS` is a 30-entry array of explicit `{sb, bb}` pairs. Level semantics:

- Levels 1–10: `sb = level*100, bb = level*200` (15-minute countdown for 1–5, 10-minute countdown from level 6)
- Levels 11–13: +500/+1000 per level (1500/3000, 2000/4000, 2500/5000), 10-minute countdown
- Levels 14–30: +1000/+2000 per level (3000/6000 up to 19000/38000), 10-minute countdown

Blind values are always shown as full integers (no `k`/thousands abbreviation) — `render()`, the menu cards, and the resume button all read `bl.sb`/`bl.bb` straight from `BLINDS`.

`fitBlind()` (via the shared `fitText()`) shrinks `#blind-inner` from its vh baseline when a wide pair (e.g. `19000 / 38000`) would overrun the available width, snapping back to full size when it fits. The container owns the font-size (`.b-num`/`.b-amp` are `1em`); `fitBlind()` is called every `render()` but early-returns unless the text or width changed, and is also wired to `resize`.

There's no special UI treatment for any level — every level (1–30) gets an identical menu card (`sb/bb`), grouped into two bordered, labeled boxes: **Rebuy** (levels 1–5, 100/200 through 500/1000) and **Freezeout** (levels 6–30, the rest), built by the menu-grid IIFE. The menu grid does highlight whichever card matches the current `level` (class `.current`, kept in sync by `updateMenuHighlight()`, called from `showMenu()`), so the grid doubles as a lightweight progress indicator.

`maxSec(lv)` encodes the duration rule and is the single source of truth for level length.

Manually changing the level (swipe/click/keyboard on the blind zone, `adjustLevel()`) only swaps which sb/bb pair is displayed — it never touches the countdown, so nudging the level up or down mid-level doesn't cost or gain time. The one exception is advancing into a level with a shorter max duration than the time currently showing (e.g. 14:00 left on 15-minute level 5, bumped up to 10-minute level 6) — that reads as broken (more time left than the level could ever hold), so `adjustLevel()` caps `remSec`/`pausedRemSec` down to the new level's own `maxSec()`, RTC-snapped like every other place that sets the countdown, so this transition stays in sync with the wall clock too. Decreasing a level never trips this: levels only get shorter (or stay the same) as level increases, so `remSec` — already bounded by whatever level it came from — can't exceed a *lower* level's max. This RTC-snap uses `capToRTC()`, not the general-purpose `snapToRTC()` — `snapToRTC()` rounds to the *nearest* `:00`, which on the half of the clock where that's forward can land up to 30s **past** the cap it's meant to enforce (e.g. 10:24 on a 10:00-max level); `capToRTC()` falls back to the same-minute `:00` on exactly that half, so the result can never exceed the cap while still landing on a wall-clock-aligned second. `adjustTime()`'s own `+1`-past-the-max capping (below) uses the same helper for the same reason.

**Level 5 (5/10) is followed by a break.** When level 5 finishes, `tick()` freezes the countdown (same shape as the Esc-hold reset) and calls `showBreakAnnounce()`, which is the only thing that still shows the fullscreen `#announce` overlay — it displays "Break" (`#ann-break`) via the `#announce.break` CSS toggle. It plays the jingle once and holds the overlay for `BREAK_HOLD_MS` (1 minute). Once that elapses (or the overlay is tapped early, via `dismissAnnounce()`), `finishBreak()` sets `level=6`, resets `remSec`/`pausedRemSec`, and returns to the blind chooser (`showMenu(false)`), so the next level is always picked manually from the menu.

### Timer loop

`tick()` computes elapsed wall-clock time from `launchWall` and derives `remSec` with `Math.ceil(pausedRemSec - elapsed)` — this makes the timer drift-resistant. Rather than polling on a fixed interval, `scheduleTick()` computes the exact ms remaining until the next whole-second boundary and schedules `tick()` to land there via `setTimeout`, then `tick()` calls `scheduleTick()` again at the end — so each digit displays for a consistent ~1s instead of drifting. At `remSec <= 0`, the level auto-advances and `levelUpCue()` fires — an alarm chime plus a quick flash on the blind numerals, with no fullscreen interruption; the countdown screen stays put and simply shows the new level.

**RTC alignment.** New levels don't just start at their full duration — `snapToRTC()` nudges the start so the countdown lands on `:00` in sync with the wall clock, and `minDriftSec()` computes the minimum correction needed after a pause so a countdown stays RTC-aligned rather than drifting by however long the pause lasted. When a level auto-advances, there's a brief `advancing=true` window (guarded by `snapTO`) between the new level's raw duration being shown and its RTC-snapped value landing (0–59s, however long it takes to reach the next `:07` mark); `freezeCountdown()` (shared by Pause and level 5 finishing) always clears `advancing` and cancels `snapTO`, so pausing mid-advance can't permanently stall `tick()`/`scheduleTick()` (both bail early while `advancing` is true).

**Display vs. real remaining time.** `displayRemSec()` (used only by `render()`, for the `#cdMin`/`#cdSec` text) is where two separate "fake it for a bit" tricks live — `remSec` itself is never touched by either; only the displayed digits lie, and only temporarily:
- *For the first `FLIP_DELAY_SEC` (31) seconds of a manually-picked level:* `snapToRTC()` means `remSec` right after picking a level is rarely a clean number (e.g. 15:13 instead of 15:00), which reads as broken to anyone who doesn't know about the RTC alignment. For `FLIP_DELAY_SEC` seconds of wall-clock time since `levelStartWall` (set in `beginCountdown()`, i.e. only on a manual pick from the menu — not on resume), it shows a plain countdown from `maxSec(level)` instead of the true `remSec`, then "flips" over to the real synced value once that window elapses. Manual `adjustLevel()` input, and `adjustTime()` input that stays under the level's max, clear `levelStartWall`, flipping to the real value immediately instead of waiting out the rest of the window. `adjustTime(1)` pushing past the level's own max is the one exception — landing on the cap reads the same as freshly picking the level, so it caps `remSec` to `maxSec(level)` and *sets* `levelStartWall` instead of clearing it, replaying the same clean-countdown-then-flip window rather than leaving an odd RTC-snapped number on screen or silently no-op'ing.
- *For the auto-advance freeze above:* rather than sitting frozen on the new level's full duration for however long `snapTO` takes to land, `displayRemSec()` counts down live from it, keyed off `advanceWall` (set alongside `advancing=true` in `tick()`). Since `updateClocks()`'s already-running 1s heartbeat (also used for the clock and the pause label) is the only thing that calls `render()` during this window — `tick()`/`scheduleTick()` both bail while `advancing` is true — it piggybacks on that same heartbeat rather than running its own interval. `adjustLevel()`/`adjustTime()` clear `advanceWall` too, for the same immediate-sync reason as `levelStartWall`.

Either way, auto-advance and the wood-clack/alarm-arming checks in `tick()` all still key off the true `remSec` throughout.

### Audio

All audio uses the Web Audio API via a small adapted `zzfx()` synthesizer (no samples, no network). `playAlarm()` synthesizes a warm ascending triangle-wave arpeggio (C5-E5-G5-C6) resolving into a shimmering two-note chime tail — used for level-advance (`levelUpCue()`) and the level-5 break (`showBreakAnnounce()`), each played once. `playWoodClack()` fires three wood-dowel-strike sounds 600ms apart, once at the 11-second mark of a level's countdown. `playSoundcheck()` is a distinct buzzy 2s tone for verifying device volume, deliberately unlike any other sound so it's never mistaken for a timer event. `stopAlarm()` clears `alarmNodes`/`alarmTimeouts` and is called from `freezeCountdown()` (so pausing silences any in-flight alarm or wood-clack) and `dismissAnnounce()`. There is no in-app volume control — alarm level follows the device's hardware volume buttons.

### Payout (prize-pool cash-count calculator)

The **Payout** button opens `#split-overlay`, a calculator wholly separate from timer state (the countdown keeps running underneath) driven by `splitRecalc()`. The user enters how many bills of each denomination (`SPLIT_DENOMS = [100,50,20,10,5]`) are in the pot; the total is the **Prize Pool** (`gross`), 90% of which (`pool`) splits across paid places per the **Payout split** selector — fixed presets Top 3 (50/30/20) and Top 4 (50/25/15/10), or Custom 3–7 Paid, whose percentages default to 1st = 50% with the rest split evenly (`defaultPcts()`/`distributeInt()`, largest-remainder rounding) and are then step-adjustable per place by 1% (`stepPct()`), redistributing whichever places are unaffected by that step so the set always sums to 100%. Custom mode percentages persist to `localStorage` (`save/loadPayoutSettings()`) and are restored if that Custom mode is picked again, across app restarts. The selector itself defaults back to Top 3 on a fresh app open, but once the user picks a mode during a session (`splitModeTouched`), `openSplit()` keeps that choice for the rest of the session instead of reverting it.

Each payout rounds to the nearest whole $5 so it can be paid in bills; the rounding difference is absorbed by the **House** cut (`gross` minus all payouts), which can therefore land a little above or below its base 10%. `greedyTake()` — the one largest-first "hand out `amount` in bills" primitive — backs both dealing a payout from the counted bills (`dealBills()`) and describing a bill breakdown (`billBreakdown()`, an unlimited-supply variant used when breaking change). A payout that can't be dealt exactly from the counted bills is a shortfall; `planBreaks()` resolves every shortfall in one pass (largest first, so a break's change carries forward to smaller ones) and reports the minimal set of bills to break — e.g. "Break 2 $20's with 2 $10's and 4 $5's." — shown as one bold red line under the Payout split selector. The House's own bill breakdown only renders once every payout balances exactly, since otherwise some of what's "left over" is really still owed to a shorted place.

### Top menu bar

`#top-menubar` is a standard left-to-right menu bar, in order: **Game** (New, Sound Check, Update, Exit) as a dropdown, then **Pause**/**Resume** and **Payout** as plain one-tap buttons, then **Help** (How to Play, Install) as a dropdown — fixed above both screens rather than living inside either one, so it's identical whether the menu (level-select) or app (running timer) screen is showing. There is no side panel anymore; every control that isn't the blind/timer swipe zones themselves lives in this bar. It's styled to the same cherrywood/glass chrome as the rest of the UI rather than literal OS gray, per the visual-design constraint below. `#btn-pause` and the Payout button are plain `.mb-label` buttons directly in the bar (not wrapped in a `.mb-item`, since they have no dropdown) — Game and Help are `.mb-item`s (`#mb-game`/`#mb-help`) containing a `.mb-label` and a `.mb-dropdown`; `toggleMenu(id)` opens one and closes any other, `closeAllMenus()` closes all (called on every button in the bar, standalone or dropdown, so a stray open dropdown can't linger open behind whatever the click just triggered), and a document-level `click` listener closes everything when the click lands outside `#top-menubar`. `z-index:41` — above both screens (`40`) but below the sound-check gate, the break announce, and every full-screen overlay (`45`/`50`/`60`), so it's naturally hidden whenever one of those covers the screen, no explicit show/hide JS needed.

`#top-menubar` paints no wood of its own — it sits directly on the real top wood border rather than in a separately-painted strip above it, the same "one continuous piece of wood, no seam" fix used for the clock notch (see below): an earlier version gave the bar its own `linear-gradient` background, which read as a second wood-look element with a visible seam against `.wood-layout`'s actual grain texture underneath. `.felt-frame`'s shared rule grows its top padding from the usual `0.25in` margin to `--top-border` (`calc(env(safe-area-inset-top) + var(--menubar-h))`) to make room for the bar's buttons at normal size — the menu screen's `#menu-felt-frame` uses this as-is, since it has no clock notch to be more clever with, so its whole top border reads uniformly thick. `#menu-screen`/`#app` no longer reserve any separate top padding of their own (removed now that the border itself provides the space), and `#top-menubar` is transparent, sized to exactly `--top-border` so its buttons land precisely over that top margin. The timer screen's `#felt-frame` overrides the shared rule back down to the plain `0.25in` on top too, since it can afford to be more precise: see the two-notch clip-path described below, which carves out the thicker `--top-border` margin only directly behind the menu bar's actual text, leaving the rest of the top edge — including the whole span under and around the clock — at the same thin margin as the other three sides.

A top-level label's click on Game or Help goes through `menuLabelClick(id)` rather than opening the dropdown directly: if the dropdown has only one *enabled* item, it skips the dropdown and runs that item immediately (neither currently has just one item, so in practice both always show their dropdown).

**Pause/Resume is one button, not two.** There's no separate Unpause button — `#btn-pause` always calls `togglePause()`, which already branches on `paused` to either freeze the countdown or resume. `updatePauseMenuItem()` keeps that one button's label (`Pause`/`Resume`) and `disabled` state (disabled whenever `!running`, since `running` stays `true` across a pause — it's only ever set `false` by a hard reset like the Esc-hold) in sync via `.mb-label:disabled`, and is called from every place `running`/`paused` change: `enterRunningState()`, `togglePause()`, the level-5 break path, and the Esc-hold reset. It's also called once at load so the button starts disabled before any level is picked.

**New** (Game menu; `resetToMenu()` internally) stops the countdown if one's running (`freezeCountdown()`) and brings up the picker screen (`showMenu()`) — the same behavior Pause itself used to have, before Pause became an in-place overlay. Unlike the Esc-hold reset, it doesn't force `level` back to 1: the current level stays highlighted on the grid, and picking any card (including the highlighted one) starts it fresh, since `selectBlind()` always resnaps `remSec`. Also clears `#pause-overlay`'s `visible` class in case New is clicked while already paused.

**Exit** (the Game menu's Exit item) calls `exitApp()` — drops full screen if active, then `window.close()` (a no-op in contexts the browser won't let a script close, e.g. a normal tab the user opened themselves rather than an installed PWA).

**Pausing stays on the timer screen** rather than navigating to the menu screen — `togglePause()` calls `freezeCountdown()` (stops the tick, stops any in-flight alarm, snapshots `pausedRemSec`/`pauseSecRTC`) and shows `#pause-overlay`, a translucent tap-to-resume layer (`onclick="resumeGame()"`) sized to exactly cover the felt (it's a sibling of `#felt-surface` inside `#felt-frame`, which is already `position:relative`, so `inset:0` matches the felt's own rounded rect). Sitting on top of `#blind-zone`/`#cd-zone` also means it silently absorbs any swipe/click that would otherwise adjust the level or time while paused. The top bar itself (`z-index:41`) sits above the overlay (`z-index:8`), so Game/Payout/Help — and Resume itself — stay reachable while paused. `enterRunningState()` clears the overlay's `visible` class every time it runs, so it can never linger into a fresh countdown even if some other path (like the Esc-hold reset) left it set.

**The felt itself strobes red/blue while paused** — `togglePause()` adds `.pause-flash` to `#felt-surface` alongside showing the overlay, which drives the `pauseFeltColor` keyframes (`6s linear infinite`, `#felt-surface.pause-flash`). Each color holds for a flat 3s span of the cycle (identical values at e.g. `0%`/`49.99%`) so the swap at the midpoint is a hard cut rather than a fade. `enterRunningState()` removes the class every time it runs (same defensive-clear pattern as `#pause-overlay`), so it can't linger into a fresh countdown. Being a plain CSS `animation`, it automatically collapses under the global `prefers-reduced-motion` rule like everything else in the app, with no special-casing needed.

**A reminder alarm nags every 30s while paused, after an initial 90s grace period** — so a forgotten paused table doesn't sit silent indefinitely. `startPauseAlarm()` (called from `togglePause()`'s pause branch) sets a 90000ms `setTimeout` to `firePauseAlarm()`, which plays two sharp square-wave beeps (`playPauseBeep()`, deliberately unlike `playAlarm()`'s warm chime so it reads as "you left this paused" rather than a level-up) and reschedules itself 30000ms later — a self-rescheduling chain rather than `setInterval`, matching how the rest of the timer logic works. Its state (`pauseAlarmTO`/`pauseAlarmNodes`/`pauseAlarmTimeouts`) is kept entirely separate from `alarmNodes`/`alarmTimeouts`/`stopAlarm()` (which `freezeCountdown()` already calls on every pause, to kill any in-flight level-up alarm) so the two can't clear each other out. `stopPauseAlarm()` is called from every place that ends the paused state on the timer screen: `enterRunningState()` (resume), `resetToMenu()`, and the Esc-hold hard reset — all three needed explicitly, since this is a live `setTimeout` chain that keeps firing regardless of which screen or overlay is currently showing.

**The clock** sits in `#felt-frame`'s top-right corner as a small white plaque with **no wood of its own at all** — a deliberate change from several earlier versions, all of which gave the clock a second wood-painted element (`.clock-rail`, matching `.wood-layout`'s gradient) and then tried to make the *seam* between that element and the real rail disappear: a rounded fillet, then a matched shadow, then a matched grain density — each attempt closed one gap and opened another (a fillet leaves a curve where the real corner is sharp; a shadow's blur re-rounds a sharp corner no blur touches; two separately-painted regions of "the same" grain pattern read as different densities at different element widths even with identical color). The fix that actually worked was architectural: stop trying to make two wood elements match, and use only one.

`#felt-surface` (the green felt, timer screen only) is clipped — `clip-path:url(#feltClip)`, a `<path>` built in JS by `layoutFeltClip()` (near `fitBlind()`) — to a rounded rect with *two* rectangular notches bitten out of its top edge. The top-right one is sized to `#clock-platform`'s own rendered footprint (`elClockPlatform.offsetWidth/offsetHeight`, measured after layout, not a hardcoded guess — the clock's digit count changes its width, e.g. `9:59`→`10:00`). The top-left one is sized to the top menu bar's actual button content (`elMbHelp.getBoundingClientRect().right` for its width, `elTopMenubar.getBoundingClientRect().bottom` for its depth — i.e. exactly `--top-border`, converted to felt-local coordinates by subtracting `elFeltSurface`'s own rect), so the felt only recedes to that thicker margin directly behind the menu text; everywhere else along the top — including the whole span under and around the clock — stays at the same plain `0.25in` margin as the other three sides, matching `#felt-frame`'s own (overridden, see Top menu bar above) top padding. Both notches are re-measured on `window.resize` and every `updateClocks()` tick, and once more from `enterRunningState()` since `render()`'s own call happens while `#app` is still `display:none` and measures 0×0. Wherever the felt is clipped away, `.wood-layout`'s background — the *only* wood-painting element anywhere in the app — simply shows through from behind, in both notches and the real rail everywhere else. There is nothing else painted in either notch, so there is nothing left that can seam; the wood there isn't *matching* the real rail, it *is* the real rail, uninterrupted. `#felt-frame`'s own `border-radius` is overridden (id-specific, so `#menu-felt-frame` keeps the shared rule's uniform rounding — its own top corners aren't notched) to leave its top-right corner square, since that whole corner is the clock's notch now rather than a rounded corner; the top-left corner stays rounded even though it's notched too, since nothing sits in it that a rounded outer corner would clip (unlike the clock, `#top-menubar` isn't a child of `#felt-frame` at all — it's a separate fixed element layered on top, so `#felt-frame`'s own `overflow:hidden` never touches it).

The wood-to-felt rim-light glow (warm highlight + dark accent) is `#felt-glow`, a plain wrapper `div` with `filter:drop-shadow(0 0 11px rgba(255,190,150,0.28)) drop-shadow(0 2px 3px rgba(0,0,0,0.5))`, sitting directly around `#felt-surface` — not `.felt-frame::after`'s `box-shadow`, which the timer screen disables (`#felt-frame::after{content:none}`; `#menu-felt-frame::after`, with no clock and no clip-path, still uses the shared `box-shadow` version unmodified). Two things forced this split, both found empirically, not from reading the spec first: `box-shadow` is generated from an element's own rectangular box with no notion of its `clip-path` — clipping `.felt-frame::after` to the notched shape (an earlier version of this fix) still only traced the felt's plain outer corners, since the notch's edges aren't real box edges, just a clip-path cut through the middle of one, and box-shadow has nothing to say about that cut. `filter:drop-shadow`, unlike `box-shadow`, projects from the element's actual *rendered alpha shape* rather than its box, so it should follow the notch correctly — but putting it directly on `#felt-surface` produced no visible shadow anywhere, notch or outer edges alike: `filter` runs *before* `clip-path` in the rendering pipeline, so the drop-shadow's source was `#felt-surface`'s pre-clip rectangular shape, and `clip-path` then clipped the combined (felt + shadow) result back down to the exact notched outline — discarding the shadow's entire outward bleed at every edge, since bleeding outward is by definition outside that outline. Moving the `filter` to `#felt-glow`, one level up, fixes it: by the time the wrapper's filter runs, it's operating on `#felt-surface`'s *already-clipped* rendered output (notch included), and `#felt-glow` itself has no clip-path of its own to discard the bleed a second time. `#felt-glow` needs no `overflow` override — it's the default `visible` — since it's not the element being clipped.

`.felt-surface`'s own inset vignette (`box-shadow: inset 0 0 14vh rgba(0,0,0,0.28), inset 0 10px 14px -8px rgba(0,0,0,0.55)` ×4 directions — the darkening that makes the felt read as recessed rather than flat) turned out to have the identical problem, just harder to notice at first: `inset` box-shadow is *still* generated relative to the element's pre-clip rectangular box, so it darkens near that rectangle's four true edges but has no notion of the notch cut through one of them — confirmed by scanning pixels inward from each boundary: a clear darkening gradient approaching the true edges, completely flat, undarkened green all the way to the notch's edges. `#felt-surface`'s id rule disables it (`box-shadow:none`) for the timer screen only (`.felt-surface`'s shared rule, hence `#menu-felt-surface`, is untouched). `drop-shadow` can't replace it here the way it replaced the rim-light — `drop-shadow` only ever paints *outside* the source alpha, and an inset vignette is by definition an *inside* effect — so this needed an actual inset-shadow technique: `#feltVignette`, an SVG `<filter>` defined next to `#feltClip`, is the standard CSS-only inset-shadow recipe (invert the source alpha with `feComponentTransfer`, blur it, flood it with black, then `feComposite operator="in"` that shadow back against the source alpha twice — once to shape it, once to clip it to only the source's own opaque area — before compositing it back over the original). Applied via `url(#feltVignette)` as the *first* step in `#felt-glow`'s `filter` chain (before the two rim-light `drop-shadow`s, so they see its output rather than the other way around) — and because it's on the wrapper rather than `#felt-surface` directly, its "source" is `#felt-surface`'s already-clipped output, notch included, so it darkens near the notch's edges exactly like it darkens near the real ones. It approximates the original 5-layer box-shadow with one unified blur (`stdDeviation="20"`, opacity `0.6`) rather than reproducing the soft-global-vignette-plus-sharp-edge-band combination exactly — close enough to read as the same effect, not a pixel-identical match.

All three of each notch's own corners are rounded too (same `16px` radius as the felt's two remaining plain corners, bottom-left/bottom-right — both top corners are spoken for by a notch now), not just the felt's plain outer corners — an early version of the merged-border fix left them sharp, on the theory (correct at the time) that rounding them was what had caused every previous seam. That reasoning applied to the *old* construction, where rounding meant adding a separate masked fillet element with its own background that had to match the real rail's color — the fillet's edge was the seam. It doesn't apply here: each notch's corners are just points on `#feltClipPath`'s single `d` string, the same path that already draws the felt's plain corners, so rounding them is a pure geometry change with no second element and nothing to seam against. For a given notch, two of its three corners (where its mouth meets the felt's own plain edges) are convex from the felt's own point of view, exactly like the felt's other outer corners, so they round the same way (`sweep-flag 1`); the third (where the notch's own two cut sides meet each other) is concave, so it needs the opposite sweep (`0`) to curve *into* the notch — a small fillet — rather than bulge outward.

`#clock-platform` is a *sibling* of `#felt-surface` (not a descendant) specifically so it isn't clipped away along with the felt in the notch area — that's exactly where it needs to render. Its `position:absolute;top:0.25in;right:0.25in` (rather than `top:0;right:0`) compensates for that: its containing block is `#felt-frame`'s own padding box (unaffected by `#felt-surface`'s `0.25in` inset), so the offset has to re-add the plain `0.25in` margin that `#felt-surface`'s own box would otherwise have absorbed on that side — the same plain `0.25in` `#felt-frame` itself uses on every side (its top margin is overridden back down from the taller `--top-border` the menu bar needs — see Top menu bar above), so the clock's own border stays a uniform `0.25in` on every side no matter which corner it's in, with no extra arithmetic needed here. Its own padding (`0 0 0.25in 0.25in`) pushes `#clock-plaque` in from the bottom/left only — the top and right sides sit flush with the notch's edges, which are themselves flush with the real rail, so nothing is added there. It carries no `box-shadow` of its own: a blurred shadow softens whatever corner it's cast from, so shadowing this box would re-round the notch's corners out of shape no matter how well anything else matched (an earlier version tried exactly this, matching `.felt-frame::after`'s glow, and re-broke the sharp corners — as they were then — it was meant to fix). Depth on the wood itself doesn't need faking any more — it's the same real wood; depth on the plaque is `#clock-plaque`'s own shadow below.

`#clock-platform` comes *before* `#felt-surface` in the DOM (unusual — visually it reads as though it belongs after) specifically so it paints behind the countdown digits if they ever overlap, without a negative `z-index`: `#felt-surface` has its own stacking context now (any element with a `clip-path` gets one, per spec, regardless of position or z-index), and giving `#clock-platform` the *usual* negative-`z-index` treatment for "sits behind" — the same trick `.suit` uses — reliably made the clock fail to paint at all next to a clip-path'd sibling in Chromium (confirmed empirically: forcing a positive `z-index` made it render again; nothing else conditionally hid it, including `#pause-overlay`, which still correctly dims the plaque along with everything else despite the reordering). Two same-level boxes (both left at the default `z-index:auto`) fall back to DOM order for stacking ties, so moving the markup earlier gets the identical "behind if they overlap" result without tripping that quirk. `pointer-events:none` (inherited by every child) means none of it ever intercepts the felt's swipe/click zones underneath. Because it lives inside `#felt-frame` (the id, not the shared `.felt-frame` class) rather than the shared bar chrome, it only shows on the running-timer screen, not the menu screen. `#mb-clock` is set 5x the size of a normal bar label, in the same `'Inter'` proportional font as the rest of the UI (bold, black) rather than a monospace or digital-segment look. Its digits sit on the plaque's white background at full `opacity` and no glow, reading like an inset display built into the felt rather than floating numerals.

**The version label** (`#mb-version`) is centered on the bottom wood border instead, in its own fixed `#bottom-bar` (not inside `#top-menubar`, since the bottom border belongs to each screen's own felt-frame rather than the shared top bar). `pointer-events:none` so it never intercepts the felt's swipe/click zones underneath it.

### Updates

The app is a PWA (`sw.js`) that runs entirely offline from its installed cache. **Check for Updates** (`#btn-check-update`, inside the top menu bar's **Game** dropdown) is the main way the app goes online: clicking it calls `registration.update()` to refetch `sw.js` and fetches `index.html` to compare the embedded `VERSION` string, showing "Latest vX.XX" (no update) or "Updated from vX.XX to vY.YY" (update found) before reloading to swap in the new version. Its resting label is the static text "Update" — the current version itself is shown beside the clock (`#mb-version`), not on this button. Unlike the other Game-menu items, clicking it does not close the dropdown — the status text needs to stay visible while it walks through "Checking…" / "Latest vX.XX" / "Updated…"; it closes itself (`closeAllMenus()`) once it settles back to the resting "Update" label. If `sw.js` changes without a `VERSION` bump, the "Latest" path also checks `swReg.waiting` and hands the already-installed worker control rather than leaving it stuck. If a new version installed in the background (service worker `waiting` state), the click posts `SKIP_WAITING` to it and reloads once `controllerchange` fires, replacing the installed app. `sw.js`'s `install` handler intentionally does not call `self.skipWaiting()` itself — that only happens on this explicit user request. `sw.js` only overwrites its cached `index.html` on a successful (`res.ok`) fetch, so a transient network error during the check can't poison the offline cache with an error page.

The only other time the app goes online unprompted is a **launch ping** — a fire-and-forget `fetch(..., {mode:'no-cors'})` to a healthchecks.io ping URL, sent once at startup right after the service worker registers. It exists purely so runs can be observed externally (healthchecks.io's Events log shows a timestamp + source IP per ping); the app never reads or awaits the response, and failures (no network, offline at the table) are swallowed silently and have no effect on startup.

### Input

Both the blind zone and countdown zone support touch (swipe), mouse (click left/right half), and keyboard (Up/Down adjusts level, Left/Right adjusts time — mirroring the swipe gestures, for keyboard/remote input at the table). Non-touch devices get visible `+`/`−` click zones via `.no-touch-only` shown when `body.no-touch` is present (set on load). Swipe directions are intentionally inverted between the two zones (blinds: right=up; timer: left=+1min). `bindSwipe()` uses an `armed` flag (set on `mousedown`, cleared on `mouseup`/`mouseleave`) so a mouse-drag that starts in one zone and ends in another can't misfire an adjustment.

### Visual design

Dark, high-contrast, glanceable-from-across-the-table is the load-bearing constraint — the blind and countdown numerals never get blur, gradients, or texture. "2026" polish (translucent `backdrop-filter` panels on the menu screen, soft shadows, inset highlights, the menu grid's current-level glow) is confined to chrome (`.menu-corner-btn`, `.pill-btn`, `.blind-card`) via the `--glass-*`/`--shadow-*`/`--inset-hi` tokens in `:root`, never to the data itself. A global `prefers-reduced-motion` media query collapses all animation/transition durations for users who request it.

`.wood-layout` (the frame behind the felt, shared by both screens) is a dark cherrywood panel — layered `repeating-linear-gradient` grain lines over a reddish-brown `linear-gradient` base, no `backdrop-filter` (an opaque wood texture has nothing to blur). It used to reserve a second grid column for a side panel; now that every control lives in the top menu bar, it's a single column and the felt fills its full width.

`#blind-zone` and `#cd-zone` share a medium-green poker-felt background (`#2e8b57`) with no other decoration — an earlier version framed them with unicode card-suit glyphs in the corners, since removed. `#cd-zone` (the felt's upper half) holds the countdown, flanked left/right by Rewind/Fast Forward `.transport-btn`s in a centered `.cd-row` (so they stay vertically aligned with the digits regardless of what's below), with Pause on its own beneath as a normal flex-column child; `#blind-zone` (the lower half) holds the current blinds, similarly flanked by a Rewind/Fast Forward pair that nudge the level down/up — but pinned via `.zone-side-btn` (`position:absolute`, edges of the zone) rather than as flex siblings, since `fitBlind()` sizes `#blind-inner`'s text off `#blind-zone`'s own `clientWidth` and would overflow if flex siblings ate into that space unbeknownst to it. DOM order is what determines which row of `#felt-surface`'s `grid-template-rows:1fr 1fr` each zone lands in, so swapping their markup order swaps their screen position, no other CSS involved. The blind `/` separator carries a small `em` side margin (`.b-amp`), matching the countdown's spaced `:` (`.cd-colon`). All `.transport-btn`s (both zones' Rewind/Fast Forward, plus Pause) are their own `position:relative;z-index:1` stacking context — needed since each zone's `.zone-half` click-catchers are absolutely positioned and would otherwise paint (and intercept clicks) on top of them.

The `#announce` overlay (the level-5 break popup — see Blind schedule above; a normal level-up no longer shows any overlay) matches the same felt green background, with its text set to white/near-white (rather than the `--dim`/`--dimmer` tones used elsewhere) for contrast against the green.
